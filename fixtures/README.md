# Wire fixtures

Golden crypto vectors and session message samples for the Android client,
generated by compiling iTerm2 v3.7.7's own Swift sources. Files the generator
writes are never hand-edited: change the generator and regenerate them.

## Harness

`harness/` is a Swift package with two targets:

- `CompanionProtocol`: the public CompanionCore protocol files.
- `WireFixtures` (executable `wire-fixtures`): the generator, compiled in one
  module with `CompanionMessages.swift` and the rest of the iOS app's shared
  sources, because the message enums are `internal`.

`harness/upstream-files.txt` lists every upstream file and its target. The
copies under `harness/Sources/*/Upstream/` are not committed.

## Regenerate

Needs a Swift 6 toolchain (macOS, or Linux with the `swift:6.2-noble` image)
and network access to gitlab.com and github.com.

```sh
cd fixtures/harness
./sync-upstream.sh            # sparse-checks out v3.7.7 and copies the listed files
swift build
swift run wire-fixtures <out-dir>
```

`wire-fixtures` reads the committed HEVC clip from
`<out-dir>/media/hevc/terminal-clip.hevc`, so run it with `<out-dir>` set to
this directory (`swift run wire-fixtures ../`). Two runs write byte-identical
files.

Off Darwin, `sync-upstream.sh` rewrites `import CryptoKit` to `import Crypto`
(swift-crypto) and applies `linux.patch`, which drops `@objc` and `NSObject`
from `iTermAIError.swift` and `StableSessionID.swift`. That patch is the only
change to upstream source. A shim for any other Darwin-only API goes in
`harness/Sources/WireFixtures/Shims/`, one file per API, with a `// shim:`
comment naming what it stands in for.

On Linux in Docker:

```sh
docker run --rm -v "$PWD/fixtures/harness:/harness" -w /harness swift:6.2-noble \
    bash -c './sync-upstream.sh && swift build'
```

## Files

- `crypto-vectors.json` (generated by `wire-fixtures`): canonical encoding,
  pairing-code parsing, room names, SAS codes, relay-join signatures for both
  roles, and Noise prologues. All bytes are lowercase hex. In `pairingCodes`,
  `upstreamOk`, `upstreamError` and the parsed fields come from upstream
  `PairingCode.parse`; `androidAccepts`/`androidReason` are the Android app's
  policy, written in `main.swift`: only a `v=1` code with a relay origin is
  accepted (`resolverUnsupported` for `v=2`, `missingRelay` for a `v=1` code
  without `relay=`, otherwise the upstream error name), and only when the
  canonical origin's host is a plain hostname (`[A-Za-z0-9._-]+`) or a
  bracketed IP literal (`[0-9A-Fa-f:.]+`), else `invalidRelay`: upstream
  percent-decodes the host, so it can hold `@`, `/`, `#`, control or non-ASCII
  characters. Join signatures are
  deterministic RFC 8032 Ed25519 only with swift-crypto's BoringSSL backend,
  so regenerate on Linux: Darwin CryptoKit randomises them.
  QR query values are percent-decoded without turning `+` into a space
  (upstream keeps a literal `+`), so Android parses the raw query with its own
  `&`/`=` splitter plus percent-decoding, never `Uri.getQueryParameter` or
  `URLDecoder`.
  The relay-origin and query edge entries (from `relayEmptyPort` on: odd
  ports, an IPv6 literal, unusual or percent-encoded hosts, empty query,
  fragment or userinfo, invalid UTF-8, a query Foundation re-encodes) record
  what `URLComponents` does in swift-foundation (`FoundationEssentials`) as
  shipped with Swift 6.2 on Linux (`swift:6.2-noble`, 6.2.4); the `Foundation`
  module there re-exports it. Darwin Foundation may differ on the exotic
  hosts; the Mac never renders those, so only the common forms must agree.
- `messages/session/*.json` (generated): session envelopes from v3.7.7, each
  `{"direction", "swiftValue", "json"}`. `json` is the envelope as upstream
  `WireCoding` encodes it, built the way the real flow builds it (iOS
  `CompanionClient`/`CompanionSession` for phoneToMac, Mac `CompanionLink`
  for macToPhone). `WireCoding.encode` writes keys in hash order, which
  changes from run to run, so `json` is the output of
  `WireCoding.makeEncoder()` with `.sortedKeys` added, embedded verbatim
  (no whitespace, `/` escaped as `\/`). Only the JSON tree is meaningful:
  compare trees, never bytes. The module prefixes in `swiftValue`
  (`WireFixtures.`, `CompanionProtocol.`) are a harness artefact.
  - `hello-phone` advertises revision 11, minimum peer 11, as this
    milestone's app does; `hello-mac` is the Mac's real reply to it, with no
    `macStatus` (the Mac sends it only to a phone at revision 14 or later).
    `hello-mac-with-alerts` is the reference reply to a phone at revision 14
    or later, not something this milestone receives.
  - Request IDs follow the Android client's order on one connection:
    `hello` 1, `relayRoomSecret` 2, `ping` 3; replies echo them; `unpairing`
    and `unpaired` have none. The Mac does not depend on the order (iOS
    sends `relayRoomSecret` first).
  - `error-reply` is the Mac's answer to `relayRoomSecret` once an unpair
    has begun (`internalError`, "This Mac is no longer paired.").
  - `main.swift` checks these call-site rules and decodes every sample (both
    upstream's bytes and the stored ones) with `WireCoding`, requiring the
    same value back.
- `messages/confirmation/{accepted,rejected}.json` (generated): the exact
  UTF-8 text of `PairingConfirmation.encoded()`, a bare JSON frame with no
  envelope, byte for byte what the Mac sends. Upstream's decode tolerates
  extra keys; Android's stricter parse of these bytes is deliberate.
- `messages/revision.json` (generated): `CompanionProtocolVersion.current`
  and `.minimumPeer` at v3.7.7, what the Mac speaks. The app advertises 11.
- `noise/xk-25519-chachapoly-blake2s.json`: the `Noise_XK_25519_ChaChaPoly_BLAKE2s`
  entry of cacophony's `vectors/cacophony.txt`, unchanged except for sorted
  keys, with the source commit in `source`. Not generated by the harness.
- `messages/live-session/*.json` (generated by `LiveSessionSamples.swift`):
  live-session envelopes from v3.7.7 in the same format and with the same
  checks as `messages/session`. Phone-to-Mac samples are built as iOS
  `CompanionClient`/`AppModel` build them (`request` for `fetchSessionTree`
  and `startSessionStream`, request IDs 4 and 5 continuing the order above,
  and 6 for the browser stream's start; `send`, no requestID, for the rest). Mac-to-phone samples follow
  `CompanionHostBridge`, `CompanionSessionStreamer`, `CompanionSessionLister`
  and `CompanionLink`; the generator cites each call site. Session names,
  titles, subtitles and chat IDs are synthetic; session `guid`s are canonical
  `ptys_` stable IDs whose check character upstream `StableSessionID`
  accepts. The phone advertises revision 13 here, which gets the unsolicited
  `sessionTree` push (no requestID).
  - `ai-availability-changed`: the Mac sends it at any phone revision once
    its hello reply has gone out, whenever AI availability changes
    (`CompanionLink.swift:549-558`).
  - `messages-removed`: the Mac forwards it only from a chat subscription's
    broker updates (`CompanionHostBridge.swift:1411-1424, 1825-1858`), and only to a
    phone at revision 12 or later. It is an unsolicited event on a chat
    subscription; `messages/agent-chat/messages-removed` is the echo of a
    phone's `deleteMessages`.
  - The session tree covers a split pane with peers beside another pane, a
    tab whose only pane has peers, a browser session, and the Mac's title
    fallbacks "Tab 3" (empty tab title) and "Window 2" (empty window title)
    from `CompanionSessionLister.swift:46-56`.
  - `send-key-special-<raw>` and `stream-ended-<reason>` use the upstream raw
    value verbatim (`send-key-special-pageUp`, `stream-ended-stoppedByClient`).
  - The stream configs carry the clip's real `codecExtradata` and its
    1280x800 size; the terminal one is an 80x25 grid of 7.875x16 pt cells
    with 5 pt side margins at scale 2, 1000 scrollback lines and 3000 lines
    of overflow (`firstAbsLine` 3000, `totalLines` 1025, `liveTop` 4000 in
    the clip's frames).
  - `stream-config-terminal-cell-geometry-absent` is a decode-tolerance case
    only, not a real host message: every Mac the phone can pair with
    (revision 11 or later) sends `cellGeometry` for a terminal. It is the
    terminal config with that optional field absent; fields the Swift struct
    always encodes (`altScreen`, `firstAbsLine`, ...) are still present.
  - `session-tree-reply-without-is-browser` and
    `stream-config-terminal-without-is-browser` are what a revision 11-14 Mac
    sends: no `isBrowser` key, which upstream decodes with `decodeIfPresent`
    as false (`CompanionMessages.swift:52-59, 401-417`). Each is upstream's
    sorted encoding with `"isBrowser":false,` cut from the JSON text; the
    harness requires upstream to decode it to the same value as the full
    sample (its `swiftValue`). They do not round-trip byte for byte:
    re-encoding adds the key back. The tree has no browser session.
  - `error-unknown-session` and `error-unknown-session-not-started` are the
    two `unknownSession` replies to a start (session gone; text view not
    sized yet, with a curly apostrophe), `CompanionHostBridge.swift:2006-2018`.
  - `stream-ended-error` is defined upstream but never sent by the Mac.
- `messages/history-and-selection/*.json` (generated by
  `HistorySelectionSamples.swift`): history tile, scroll-wheel and selection
  envelopes from v3.7.7, same format and checks as `messages/session`. They
  continue the live session: stream 1, generation 1, window
  [3000, 3000 + 1025), liveTop 4000. `fetchHistoryTile` (request ID 7) and
  `copySelection` (8) are requests, as iOS `CompanionClient` sends them; the
  rest are `send`s. Replies and errors echo those IDs; `streamExtent` and
  `selectionRange` are unsolicited.
  - `fetch-history-tile` asks for the first 50-line slot (3000, 50 lines);
    `history-tile` is the Mac's reply clamped by upstream
    `CompanionHistoryWindow`. Its `pngData` is NOT the Mac's renderer output
    (AppKit's `renderImage`/`dataForFile`, unavailable off macOS) but a
    minimal valid PNG: one 8-bit grayscale black pixel with a stored deflate
    block, so it is byte-identical everywhere. A real tile is
    `lineCount * cellHeight` by `columns * cellWidth` encoded pixels.
  - `history-tile-evicted`: the same request after 100 more lines scrolled
    off; the Mac replies with 0 lines, empty `pngData`, at
    `max(requested, overflow)` (`CompanionHostBridge.swift:2124-2134`).
    `stream-extent` is that trim.
  - `history-tile-clamped`: a 50-line request at 3050 after the overflow
    reached 3080, clamped by `CompanionHistoryWindow` to the 20 lines left:
    the reply starts at 3080, not where the phone asked.
  - `selection-gesture-begin-<mode>` for every `CompanionSelectionMode`
    (iOS itself only begins in `character`); move and end are `character`.
    `selection-range` is the inclusive span after that drag;
    `selection-range-cleared` has no `range` key (Swift omits a nil).
  - `error-no-such-stream`: the reply to a tile request for a stream the Mac
    does not have (`CompanionHostBridge.swift:2115-2120`).
- `messages/browser-sessions/*.json` (generated by `BrowserSamples.swift`):
  browser input, browser navigation and Mac status envelopes from v3.7.7,
  same format and checks as `messages/session`, on the browser stream
  (stream 2). Every phone-to-Mac browser message is a `send` (no requestID),
  as iOS `CompanionClient` sends it; the Mac-to-phone ones are unsolicited.
  - `hello-phone-revision-fifteen`: the app's hello from revision 15 on; the
    Mac's reply then carries `macStatus` (`hello-mac-with-alerts`).
  - `browser-tap` has a fractional `x` and an integral `y` (written `300`).
  - `browser-navigation-changed-minimal`: decode tolerance only, the state
    with every field removed (upstream reads absent strings as `""` and
    absent booleans as false); a v3.7.7 Mac always writes them all. Checked
    like the older-Mac samples: it decodes to the empty state.
  - `modal-alert-answer-rejected`: the Mac sends it only after an
    `answerModalAlert`, which this app never sends.
- `messages/agent-chat/*.json` (generated by `AgentChatSamples.swift`): chat
  envelopes from v3.7.7, same format and checks as `messages/session`.
  Phone-to-Mac samples are built as iOS `CompanionClient`/`AppModel` build
  them; Mac-to-phone samples follow `CompanionHostBridge`; the generator cites
  each call site. Chat titles, message texts, session, workgroup and model
  names are synthetic; chat IDs, message UUIDs and workgroup IDs are fixed
  uppercase UUIDs; session guids are the `SyntheticMac` stable IDs of
  `messages/live-session`, plus legacy UUID guids where the Mac keeps one (a
  Mac-made session chat's `terminalSessionGuid`, a `session:<uuid>` mention).
  - Revision: the app advertises 15. Every Mac gate a chat message depends on
    (`turnLifecycle` at 8, `messagesRemoved` at 12, the typed `aiUnavailable`
    error at 13, `muted` at 5) holds at 13 and at 15 alike, so the samples are
    the same for either; the harness checks this.
  - Request IDs continue the order on one connection after
    `messages/history-and-selection` (which ends at 8): list 9, create
    (orchestrator) 10, create (session) 11, subscribe 12, resolve mentions 13,
    workgroup info 14, session screen info 15. Replies and errors echo them.
    `unsubscribe`, `publish`, `delete-chat`, `delete-messages` and
    `set-chat-muted-*` are `send`s (no requestID); every event has none.
  - `publish-plain-text`: the five keys of an iOS user message
    (`chatID`, `author`, `content` = `{"plainText":{"_0":text}}`, `sentDate`,
    `uniqueID`), `partial:false`; the text is trimmed and holds a mention, a
    newline, `/` (written `\/`), an emoji and non-ASCII letters. The harness
    fails if a publish has another key or a phone-sent date is not a whole
    number of milliseconds.
  - `history`: the orchestrator chat's visible history, one message of every
    `Content` case the Mac forwards in a history (every case not
    `hiddenFromClient`, less the streaming `append`/`appendAttachment`, which
    exist only as deliveries, and `unsupported`, never encoded): `plainText`
    with and without `context`, `markdown`, `multipart` with every `Subpart`
    and every attachment type (`code`, an image `file`, a non-image `file`,
    `fileID`, `statusUpdate`), `explanationRequest`, `explanationResponse`,
    classic and external `remoteCommandRequest`, `watcherEvent`,
    `selectSessionRequest`, `clientLocal` with each of the ten actions, and
    `terminalCommand`. It collects kinds for decoding; it is not one plausible
    conversation. `explanationRequest`/`explanationResponse` are decoded from
    hand-written JSON by upstream's decoder (their `iTermCodableLocatedString`
    only decodes on iOS) and re-encoded; `gridCoords` follow the Mac's
    `GridCoordArray`/`VT100GridCoord` coding. Its last `sentDate` is the one
    fractional date in the chat samples (`1795000400000.25`); every other date
    is whole milliseconds. The harness fails if a case, an action, a subpart or
    an attachment type is missing, and checks that the cases it leaves out are
    still hidden or still visible upstream.
  - `history-empty`: a subscribe to an unknown or deleted chat gets an empty
    history with `maxSeq` 0, not an error (`CompanionHostBridge.swift:2229-2239`).
  - `chats-and-sessions`: three chats, most recently bumped first: an
    orchestrator chat (`claimedScopes` with a `wg-` ID and a `session:` scope,
    one watcher, a 1x1 PNG `icon`), a muted session-bound chat whose snippet is
    upstream `snippetText(maxLength: 200)` of a longer reply (exactly 200
    characters, ending `…`), and a chat with no snippet. `chats-and-sessions-ai-off`
    has no chats and the same sessions.
  - `chat-created` (orchestrator, `orchestrationEnabled` true) and
    `chat-created-session` (the session's guid as `terminalSessionGuid`): no
    snippet, since the only message is the hidden `setPermissions`, whose
    append bumps `lastModifiedDate` a few milliseconds past `creationDate`
    (`ChatBroker.swift:120-131`, `ChatListModel.swift:313-314`).
  - `mentions-resolved` answers `resolve-mentions` in order: a stable ID hit,
    a `session:<legacy uuid>` hit that reveals by the session's stable ID, a
    workgroup hit whose `sessionGuid` is its leader, and a miss with only
    `identifier`.
  - `workgroup-info`: members in `idle`, `working`, `waiting`, `unknown`, and
    one not launched (no session, state `unknown`).
  - `session-screen-info`: fractional `width`, `lineHeight` and `scale` to pin
    number decoding (a real Mac's scale is 1 or 2).
  - Errors: `error-ai-unavailable` (to an AI-only request, here subscribe),
    `error-unknown-workgroup`, `error-unknown-session` (to the screen info
    request), and `error-delete-refused`: unsolicited, no requestID, because
    `deleteChat` is a send; its text is the Mac error's description, here
    "The chat system is not available".
  - Deliveries: `partial` is true exactly for `append` and `appendAttachment`.
    `delivery-user-echo` is `publish-plain-text`'s message unchanged. The
    `append*` deltas name `delivery-agent-opening`'s message (checked).
    `messages-removed` is the Mac's echo of `delete-messages` (the history's
    last two messages): the truncated suffix of its store in store order,
    which includes a hidden `remoteCommandResponse` row the phone never saw
    (`...0350`) and leaves out a chat-state `setPermissions` row inside the
    range (`ChatBroker.swift:188-196`, `ChatListModel.swift:246-263, 283-290`).
    So it names three IDs where the phone asked for two.
    `chat-list-changed` is the list after `delete-chat`.
- `chat/*.json` (generated by `ChatVectors.swift`): upstream behaviour for the
  chat code, pretty-printed with sorted keys; embedded messages are encoded as
  the wire encodes them (dates in milliseconds).
  - `decode-tolerance.json`: `[{name, json, upstream, upstreamValue?,
    upstreamError?, android?}]`. `json` is the exact text to decode as a host
    envelope; `upstream` is upstream `WireCoding`'s verdict, which the harness
    checks; `upstreamValue` is what it decoded, re-encoded; `upstreamError` is
    the DecodingError's kind and coding path; `android` says where the app
    deliberately differs. Verdicts: a future content case and a future
    `clientLocal` action decode as `unsupported`; turn event `"paused"` decodes
    as `unknownFuture`; chats without `muted` (a pre-5 Mac) decode as nil; a
    hello without `aiAvailable` (a pre-13 Mac) decodes as nil, which the app
    reads as true; a workgroup member state `"sleeping"` is **rejected**
    (Android reads `UNKNOWN`); a known content case with a corrupt body is
    **rejected** with the whole frame (Android keeps the frame, that message's
    content `Unreadable`), while a future case in the same history degrades
    only that message; a classic remote command with an unknown tool is
    **rejected** (Android keeps the message as `Unreadable`).
  - `streaming-merge.json`: `[{name, chatID, transcript, deltas, expected}]`.
    `expected` is `transcript` after each delta is applied with iOS's merge
    rule (`AppModel.swift:5215-5277`), ported line for line in the generator
    (AppModel is not compiled) over upstream's compiled `Message.append` and
    `Attachment.appending`: upsert by `uniqueID`; `append` changes only a
    `plainText`, `markdown` or `multipart` target (a `plainText` target loses
    its `context`); `appendAttachment` likewise; a delta for a missing target
    starts an agent message dated by the delta; `commit` is ignored. Cases
    include code attachments with the same and different `id`s, status
    updates (always coalesce), files with the same `id` (names, bytes and MIME
    types concatenate), the user echo, and a 1 000-delta reply.
  - `mention-parser.json`: `{"cases": [{name, text, atSignOptional, mentions:
    [{location, length, prefix, token, identifier}]}], "split": [{name,
    identifier, prefix, token} | {name, identifier, invalid: true}], "protect":
    [{name, text, indentedCodeBlocks, mentions: [{location, length, identifier,
    protected}], protectedText}], "canonical": [{name, input, canonical}]}`
    from `MentionParser.mentions(in:atSignOptional:)` (UTF-16 offsets),
    `MentionParser.split(identifier:)`, `MentionParser.protect` and
    `StableSessionID.canonical`; `prefix` is null for a bare reference and
    `canonical` null for an invalid input. `protect`'s span regexes
    (`MentionParser.swift:125-148`) are private, so `protect` records their
    effect: every mention protect finds (it scans with `atSignOptional` true)
    and whether it replaced it, i.e. whether it lies outside every code span,
    fenced block, link destination, autolink and bare URL (and, with
    `indentedCodeBlocks`, every indented code line). `protectedText` is
    protect's output with its random nonce written `NONCE`.
    Upstream's regex admits only the strict stable ID alphabet (case-folded),
    so a Crockford-confusable stable ID (`l` for `1`, `O` for `0`) is not a
    mention and does not split; only `StableSessionID.canonical` folds case
    and confusables; an `@`-signed stable ID with a wrong check
    character is a mention whose token is left as written.
  - `status-update-display.json`: `[{name, statusUpdate, displayString}]` from
    `LLM.Message.StatusUpdate.displayString`.
  - `remote-command-description.json`: `[{name, remoteCommand, functionName,
    permissionCategory, markdownDescription}]` from the compiled
    `RemoteCommand`: all 26 `Content` cases with default arguments (named by
    case), then `executeCommand`, `insertTextAtCursor` and `getManPage` with
    arguments of exactly 32 and 33 characters, with backticks, with a backtick
    escaped across the cut, and with a ZWJ emoji at character 32 (the cut
    counts `Character`s after escaping backticks, iOS `MacShims.swift:22-27`),
    plus realistic arguments for the other interpolating descriptions. The
    harness fails if a case is missing.
- `media/frames.json` (generated by `MediaSamples.swift`):
  `{"valid": [...], "invalid": [...]}`. Valid entries come from
  `CompanionMediaFrame.encoded(version:)` and decode back to the same value
  with `init(decoding:)`; `generationId`/`liveTop` are present for version 2
  only. Invalid entries are byte strings `init(decoding:)` rejects, with
  `upstreamError` as `String(describing:)` writes the error. Every entry has
  `channelHex` = `CompanionFrameChannel.frameMedia(encodedHex)`.
- `media/parameter-sets.json` (generated): `{"valid": [{name, setsHex,
  containerHex}], "invalid": [{name, containerHex, upstreamError}]}` from
  `encodeParameterSets` / `decodeParameterSets`. Upstream ignores bytes
  after the last set, so trailing data is not an invalid case.
- `media/access-units.json` (generated): `{"valid": [{name, nalUnitsHex,
  payloadHex}], "invalid": [{name, payloadHex, upstreamError}]}` from
  `encodeAccessUnit` / `decodeAccessUnit`.
- `media/hevc/terminal-clip.hevc`: 15 frames of 1280x800 HEVC Main,
  Annex-B, made by `media/make-hevc-clip.sh` and committed. VPS/SPS/PPS are
  in band before each IDR; IDRs (NAL type 20) at frames 0 and 10, P-frames
  between, no B-frames, no SEI. Made with ffmpeg 6.1.1-3ubuntu5 (Ubuntu
  24.04.5) and libx265 3.5 (`libx265-199` 3.5-2build1, build string
  `3.5+1-f0c1022b6`), x265 parameters
  `bframes=0:keyint=10000:min-keyint=10000:repeat-headers=1:aud=0:open-gop=0:info=0:frame-threads=1`.
  Beyond the plan's parameters: `open-gop=0`, because without it this x265
  codes the second forced keyframe as a CRA (type 21), not an IDR, even with
  `-forced-idr 1`; `info=0`, which drops x265's informational SEI (it
  records the CPU flags and thread count); `frame-threads=1`, so the output
  does not depend on the number of CPUs (identical bytes with 1 and 4 CPUs).
  Another x265 build can still produce a different file. The committed clip
  is the reference; regenerate it only on purpose, then rerun the harness.
- `media/hevc/terminal-clip.json` (generated): the clip as the Mac sends it.
  The harness splits the Annex-B stream into access units, moves the
  parameter sets into `codecExtradata` with `encodeParameterSets`, packs the
  rest of each access unit with `encodeAccessUnit`, and
  wraps each in a version 2 `CompanionMediaFrame`: stream 1, sequence from 0,
  pts from 523118042 ms in 33 ms steps, generation 1, `liveTop` 4000.
  Frame 0 has flags `keyframe|configChanged` (3): the stream's first
  keyframe, the one its config (generation 1) was built from. Frame 10 has
  flags `keyframe` (1): an insurance keyframe, which the Mac sends 0.3 s after
  the last P-frame with nothing new (`CompanionSessionStreamer.swift:374-382`).
  It comes from the same encoder, so it carries the same parameter sets, and
  no config is resent (`CompanionSessionStreamer.swift:561-597`). A decoder
  must keep its codec across a keyframe without `configChanged`; only a new
  config replaces it. The pts steps stay 33 ms throughout, although a real
  insurance keyframe follows at least 300 ms of quiet. The harness fails if the first VCL NAL of frames 0
  and 10 is not IDR, if any packaged access unit holds a VPS/SPS/PPS, or if
  `codecExtradata` lacks one each of them. `media/check-terminal-clip.sh`
  then rebuilds Annex-B from `codecExtradata` and frames 10-14 and decodes it
  with `ffmpeg -v error`, expecting 5 frames and no error.
