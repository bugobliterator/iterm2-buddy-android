# Agent Chat Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** From the Pixel, the owner talks to the AI agents (Claude Code and iTerm2's own AI chats) running in iTerm2: lists chats and sees at a glance which agents are working, done or waiting; opens a chat and watches the reply stream in; sends messages with @-mentions of sessions; creates, mutes, deletes and truncates chats; and opens a workgroup to see each member agent's state.

**Architecture:** Chat-scoped messages from the Mac (`history`, `delivery`, `typingStatus`, `turnLifecycle`, `messagesRemoved`, `chatListChanged`, the chat-list and create replies, `aiAvailabilityChanged`) never touch the 64-slot, dropping `events` flow. The session's receive loop hands them, in wire order and bracketed per link, to an app-scoped `ChatRepository` through a second ordered, non-dropping sink, exactly as stream-scoped messages reach the `StreamController` today. The loop never parses a big chat body: `history`, `chatsAndSessions` and `chatListChanged` cross as raw bytes, and the repository's accept only enqueues into a bounded inbox drained by one consumer that never awaits the Mac. The repository owns the chat list, the per-link subscription set (every listed chat is watched), each open transcript (streaming deltas merged as iOS merges them), a per-chat activity state machine fed by `turnLifecycle` and request latches (typing is only the spinner), unread marks, and AI availability. Compose screens render its flows. A `HomeNavigator` with a Chats tab and a Sessions tab replaces the single-tab `SessionNavigator`; opening and closing a conversation, like a stream, is driven only by navigator calls.

**Tech Stack:** Kotlin 2.4, Jetpack Compose (Material 3, `NavigationBar`, `LazyColumn`, `TextFieldState` with input/output transformations), kotlinx-coroutines, kotlinx-serialization-json (tree API). Tests: JUnit 4, kotlinx-coroutines-test, the in-process fake relay and `FakeMac`. Fixtures: the Swift harness (Swift 6.2, `swift:6.2-noble` in Docker). No new runtime dependency.

**Spec:** `docs/superpowers/specs/2026-11-15-android-companion-design.md` (Goals 2, "What the owner experiences → Chat", Phases → Agent Chat), its protocol notes `docs/superpowers/specs/2026-11-15-protocol-notes.md` (App layer → Message catalogue, History and live events, Sending), and the Sessions notes `docs/superpowers/specs/2026-11-16-sessions-protocol-notes.md` §1 (revisions and gates). The rules and rulings in `docs/superpowers/handoff/2026-11-15-pairing-milestone-handover.md` apply unchanged.

Request bounds, all injectable: list 15 s (`AM:2223`), subscribe 15 s (`AM:2939`), workgroup 15 s (`AM:4287`), session screen info 15 s (`AM:4249-4253`), create and resolve the client's `rpc` 15 s.
- **Byte-exact wire parity.** Every phone→Mac chat message has an upstream sample, and its parity test passes two ways: the JSON trees are equal, and the Kotlin encoding re-serialised in the samples' canonical form (keys sorted, no whitespace, `/` written `\/`, non-ASCII as raw UTF-8, numbers as Swift writes them via `swiftDouble`) equals the sample's `json` text **byte for byte**. Every new Mac→phone case has a sample and a decode test. A mismatch is a failure.
- `UUID` fields (message `uniqueID`, `messageIDs`, `append.uuid`) are encoded as **uppercase** canonical strings, decoded case-insensitively and held uppercase (Swift `UUID`, `MS:509`). `Date` fields are milliseconds since 1970 as a JSON number (`WireCoding.swift:15-25`); decode accepts any number literal into a `Double`; the phone only sends whole milliseconds, written as an integer literal.
- The published user message is exactly `{"chatID", "author":"user", "content":{"plainText":{"_0":text}}, "sentDate", "uniqueID"}`, nothing else (`AM:3100-3118`, `MS:286-287`); `context`, `inResponseTo`, `responseID`, `agentReasoning`, `configuration`, `firstBlobRef` are omitted (nil). Text is trimmed of leading and trailing whitespace and newlines; empty text is never sent (`AM:3087-3091`).
- Forward compatibility, as upstream: an unknown `Message.Content` discriminator or an unknown `ClientLocal.Action` decodes to `Unsupported` content, not an error (`MS:732-758`, `MS:191-215`); `TurnEvent` unknown raw value decodes to `UNKNOWN_FUTURE` (`MS:68-81`). Android leniencies, each tested and named here: an unknown `SessionState` raw value decodes to `UNKNOWN` (upstream's synthesized enum throws, `WW:170-175`, and would lose the whole `workgroupInfo`); a message whose content body is corrupt is kept as `Unreadable` content instead of failing the whole `history` frame (upstream fails the frame, `MS:744-757`), while a corrupt `chatID`, `author`, `sentDate` or `uniqueID` still fails it.
- **Chat-scoped messages never reach `CompanionClient.events`** (a `MutableSharedFlow` with `extraBufferCapacity = 64` and `tryEmit`, which drops when full, `AND/core/CompanionClient.kt` `emitEvent`). They go to the ordered chat sink (*Chat Channel*): suspending, back-pressured, never dropped, bounded only by `ClientTimeouts.sinkStall`.
- **The receive loop never waits on chat work.** The chat sink's `accept` only enqueues into `ChatInbox`, bounded by items **and** bytes (`ChatBudgets(inboxItems = 4096, inboxBytes = 16 MiB)`, an input over the byte bound admitted only into an empty inbox, as the `StreamController` inbox, `AND/core/stream/StreamController.kt` `StreamBudgets`). One consumer drains it; it never awaits a Mac reply, and every request (list, subscribe, create, resolve, workgroup) runs in its own coroutine whose outcome comes back through the inbox. Accept runs under the session's stream lock while the loop waits (`AND/core/CompanionSession.kt:473-498`), so anything else is a `sinkStall`, a lost link, and a resubscribe of every chat that stalls again. A link brings two `LinkUp` markers (stream, then chat), each allowed `sinkStall`: the control chain's worst case before `Connected` is twice `sinkStall`, accepted because neither sink blocks in practice.
- **The receive loop never parses a big chat body.** After decrypting a frame, `peekEnvelope` reads the request ID and the payload's one case with a single allocation-free scan. `history`, `chatsAndSessions` and `chatListChanged` go to the sink as raw bytes (`ChatInput.Payload`) and are decoded by the inbox consumer; every other case decodes on the loop as today. Decode errors in the consumer drop that payload (upstream drops the frame too) and are logged by case and key only.
- **Raw chat cap.** A raw chat frame (`history`, `chatsAndSessions`, `chatListChanged`, or a `delivery` routed raw because it is over 256 KiB) whose plaintext is over `maxRawChatBytes` (**8 MiB**, injectable; well under the 32 MiB Noise cap) is never parsed: judged by its length after the linear, allocation-free peek, its bytes are dropped on the loop and the sink gets `ChatInput.PayloadTooLarge(linkId, case, chatID?, requestID?, sizeBytes)`; a too-large history makes that chat show `TooLarge`. Streaming decode is a later phase. Memory tests assert **peak** allocation (a bounded-heap JVM and allocated bytes per input byte), never retained heap and never wall-clock time.
- **No content in logs or `toString`.** Chat titles, snippets, message text, attachment names and bytes, mention display names, session names in mention picks, workgroup and role names, `statusText`/`detailText`, drafts, search queries and chat icons are never logged. Chat IDs, message UUIDs, session GUIDs, workgroup IDs, counts, sizes, case names and revisions may be. Every type that carries such content overrides `toString()` to show lengths only, and has a sentinel test: `ChatSummary`, `ChatListEntry`, `ChatMessage`, `MessageBody` (every case), `Subpart`, `Attachment`, `MentionResolution`, `WorkgroupMember`, `WorkgroupInfo`, `UserTextMessage`, `PhoneMessage.Publish`, `PhoneMessage.CreateChat`, `MacMessage.History`, `MacMessage.Delivery`, `MacMessage.ChatsAndSessions`, `MacMessage.ChatListChanged`, `MacMessage.ChatCreated`, `MacMessage.MentionsResolved`, `MacMessage.WorkgroupInfoMessage`, `SessionScreenInfo` (the session name), `ChatInput.Message`, `ChatInput.Payload`, `ConversationState`, `ChatListState`, `TranscriptItem`, `MentionDraft`, `ChatSearch`, `MergeResult.Ignored`, `SendOutcome.NotSendable`, `WorkgroupState.Failed`, `CommandContent`, and `MacMessage.Error` (its `message` is Mac text that can interpolate a Swift error, `HB:468`, `HB:1406`; code only). Chat decode exceptions name keys and cases, never values, and never carry a kotlinx exception's message (it quotes the input); a sentinel test pins it.
- Memory budgets, all injectable: full transcripts are kept only for conversations on the navigation stacks plus the **3** most recently closed (iOS keeps only mounted ones, `AM:2844-2846`); file attachment bytes are kept only for `image/*` up to **4 MiB** each and **32 MiB** per transcript (others keep name, type and size); decoded inline images share one **48 MiB** bitmap budget; chat icons are decoded once per content hash into a **2 MiB** cache. Over a budget, bytes are dropped and the item shows its name, never an exception.
- The Noise reassembly cap stays 32 MiB (`DEFAULT_MAX_MESSAGE_BYTES`, `AND/core/noise/NoiseChannel.kt`). A `history` over it ends the link (`LinkDown(messageTooLarge = true)`); the subscribes still unanswered (no history, too-large or error reply; a phone-side timeout does not answer one) become suspects, retried first and alone on later links until the culprit is the only one out, which is marked too large and never re-subscribed automatically (*Chat Repository*).
- Approvals and notifications are out of scope: the phone never sends `remoteCommandDecision`, `selectSessionResponse`, `linkSession`, a `userCommand` publish, `pushStatus`, `syncSince`, `messagesSince` or `notificationPermissionResponse` in this phase. A test pins that no chat path can produce them.

## Review Focus

- **Streaming replies stay in order across reconnects.** A reply is a full opening `delivery` followed by `delivery` messages whose content is `append(string, uuid)` or `appendAttachment(attachment, uuid)` naming it (`HB:1825-1869`); `.commit` is hidden and never forwarded (`MS:549-562`), so the end of a turn is `turnLifecycle(ended)` only (`CS:494-505`). The Mac sends `history` and then the subscribe snapshot before any live delivery on that subscription (`HB:1411-1443`), and its control lane is never dropped or reordered (`sources/Companion/CompanionPriorityOutbox.swift:5-21`). The phone keeps that order end to end: the history reply and every delivery pass through one ordered sink, a history **replaces** the chat's transcript at its wire position, and nothing from an older link is applied after a newer link's history. Pinned in *Chat Channel* (`historyReplyPrecedesLiveDeliveriesInSink`, `chatInputsFromAnEndedLinkAreDropped`) and *Chat Repository* (`resubscribeOnReconnectReplacesTranscript`, `deltaBeforeHistoryOnNewLinkIsNotApplied`).
- **At-least-once versus duplicates.** Within a link every chat event arrives exactly once. Duplicates come from three places, each handled: the phone's own published message comes back as a `delivery` with the same `uniqueID` (`HB:1812-1823`) and is upserted, never appended twice; a second `subscribe` re-sends the whole history (`HB:1417`), which replaces rather than merges, so append deltas are never applied twice; and a delivery for a chat the phone has no transcript for is dropped (iOS merges only into an existing snapshot, `AM:4296-4313`). Pinned in *Transcript Merge* and *Chat Repository* (`ownEchoIsUpsertedNotDuplicated`, `secondHistoryReplacesWithoutDoubleAppend`).
- **The subscribe lifecycle per link.** Subscriptions live and die with the Mac's bridge, i.e. with the link (`AM:2427-2438`, `AM:3072-3074`); the Mac's subscription is not reference-counted and a later `unsubscribe` cuts a fresh one (`HB:489-493`, `AM:3040-3062`); turning AI off drops every subscription on the Mac and turning it back on does **not** restore them (`HB:2250-2269`, `AM:4470-4486`). The Mac installs a subscription **before** it sends the history (`HB:1411-1427`), so a subscribe that times out on the phone is still installed and its history still arrives. Owner decision: **every listed chat is watched**, plus the open conversation. One owner (`ChatSubscriptions`) computes the wanted set and diffs it on each link, list change, navigation change and AI flip. Subscribed state is **derived from the sink**: a `History` (or a history `PayloadTooLarge`) on link N means subscribed on link N; the request's outcome only drives the Loading banner, and a late `History` is applied when it lands. A chat subscribed or subscribing on this link is never subscribed again on it (only Try again does that); subscribes run in their own coroutines, at most `subscribeConcurrency` (2) out at once; an unsubscribe is never sent for a chat still wanted. AI off clears the link's subscribed set, since the Mac dropped them. Pinned in *Chat Repository* (`subscriptionsAreReissuedOnEveryLink`, `unsubscribeNeverCutsAWantedChat`, `aiBackOnResubscribesWantedChats`, `lateHistoryAfterTimeoutIsApplied`, `listChurnDoesNotResubscribe`) and *Chat Subscriptions and Seen Marks* (`subscribedOnThisLinkIsNeverPlannedAgain`).
- **The receive loop never waits on the chat feature.** Accept enqueues and returns; the consumer never awaits the Mac; big bodies cross as raw bytes and decode in the consumer, so a live stream's frames never queue behind a history decode. Pinned in *Chat Channel* (`historyAcceptReturnsWithoutDecoding`, `bigChatBodiesCrossAsRawBytes`) and *Chat Repository* (`acceptNeverWaitsForAReply`).
- **Turn lifecycle versus typing edges.** "A mid-turn park corrupts typing edges" (`CPV` revision 8 note, `MSG:1031-1037`): typing goes false while a turn is parked on the user and true again on resume, while `TurnStatusModel` stays in progress across the park (`sources/AITerm/ChatListModel.swift:776-802`). Working/done/waiting therefore come from `turnLifecycle`, with typing only splitting *working* from *parked*. The subscribe snapshot re-seeds `typingStatus(true)` and `turnLifecycle(started)` only when they hold (`HB:1091-1107`), so a `history` reply is the reset point and a lost link makes state unknown, never stale. Transient edges (typing false just before `ended`, `started` just before typing true, `CS:688-695`) must not flash "Waiting". Approval parks (a classic command, and the select-session request it becomes when no session resolves, `ChatClient.swift:126-142`, `CA:2203-2227`) and enable-orchestration parks clear typing (`CA:240-263`); only an orchestration tool call parks with typing **true**, while a workgroup-permission request waits (`CA:160-167, 453-458`), so a blocking request latches Waiting whatever typing says. A turn that ends during a drop leaves no `ended` and no snapshot `started`, so Done is a latched fact that survives `LinkDown` and `history`. Pinned in *Chat Activity* (`parkShowsWaitingAfterDebounce`, `endOfTurnTypingEdgeDoesNotFlashWaiting`, `requestWithTypingOnIsWaiting`, `resumeAfterRequestClearsWaiting`, `historyResetsTurnState`, `linkDownMakesStateUnknown`, `doneSurvivesReconnect`, `turnEndedDuringDropShowsDone`).
- **Mention resolution.** The phone parses mentions with a port of `MP` (case folding of a matched stableID through `SSID:61-110`; Crockford-confusable stableIDs are NOT matched by the parser, whose class is the strict alphabet, `MP:30`, `SSID:44`; only `canonical()` folds them) checked against upstream vectors; resolutions are cached only on a hit, misses go to a retry gate reopened on chat open and reconnect (`AM:4171-4226`); a mention inside a code span is not linkified and markdown cannot eat a stableID's underscores (`MP:108-190`). Composer tokens serialise to `@<guid>` (`IOS/Views/MentionComposerView.swift:105-120`). Pinned in *Mentions* (`parserMatchesUpstreamVectors`, `missIsRetriedAfterReconnect`) and *Composer and Send* (`draftSerialisesTokensAsGuids`).
- **Unread and "done".** Every committed message bumps the chat (`CLM:122-129`) and the Mac pushes the whole list 0.5 s later (`HB:166-179`, `HB:277-292`); the phone's own publish bumps it too. A chat is unread only when it moved after the owner last saw it **and** the change was not the owner's own words, sent from the phone or typed on the Mac; a turn that ends while the conversation is visible is not unread; marks survive process death and are wiped on unpair. Seen marks hold the Mac's `lastModified` and are compared only with later Mac values, never with phone time. Pinned in *Chat Repository* (`ownSendDoesNotMarkUnread`, `macTypedMessageDoesNotMarkUnread`, `turnEndedWhileVisibleIsRead`) and *Chat Subscriptions and Seen Marks* (`seenMarksSurviveRestartAndClearOnUnpair`).
- **Large histories, paging and memory.** The protocol has no paging: `subscribe` returns the entire visible history in one frame (`HB:2229-2239`), again on every reconnect. The tree decode of a history holds the bytes, a UTF-16 string twice their size and a `JsonElement` tree several times that at once, so the peak, not the plaintext, is what kills the process (Pixel 9 heap limit 256 MiB without `largeHeap`). Hence the 8 MiB chat history cap judged by length before parsing, decode in the consumer off the receive loop, one history decoded at a time, and a history over the Noise cap ending the link without a resubscribe loop; transcripts, attachments and icons are under byte budgets; the conversation list is lazy and re-renders only the bubble that changed. Pinned in *Chat Channel* (`historyOverTheChatCapIsNeverParsed`), *Chat Repository* (`tooLargeHistoryIsNotResubscribedInALoop`, `oversizeWithConcurrentSubscribesIsolatesTheCulprit`, `closedTranscriptsAreEvictedBeyondThree`), *Chat Content Model* (`capSizedHistoryDecodesInABoundedHeap`, `decodeAllocationIsLinearInSize`) and *Conversation* (`streamingDeltaRecomposesOnlyItsBubble`).
- **Sending interacts with a pending approval.** A message typed while the agent is parked abandons the request only when `isAwaitingUserApproval` holds and no approved command is executing (`CS:229-237`, `CA:1289-1292`, GitLab #12984): a classic command approval or an enable-orchestration request. Select-session and workgroup-permission requests are not abandoned, and an `executingCommand` notice means the command already runs. The composer warns only for the abandonable two. Pinned in *Composer and Send* (`pendingRequestWarnsBeforeSend`, `warningOnlyForAbandonableRequests`).
- **A send can fail silently on the Mac.** The echo comes only through the subscription; the Mac swallows publish errors (`try?`, `HB:1822`) and drops a fire-and-forget publish while AI is off (`HB:2289-2293`); it does not dedupe appends (`CB:146-160`). So Send needs a history received on the current link, an echo that does not come within `echoTimeout` (10 s) marks the bubble "Not delivered" with Retry (a new `uniqueID`), and a history that replaces the transcript keeps unacknowledged echoes as "Not delivered". Pinned in *Composer and Send* (`echoTimeoutMarksNotDelivered`, `sendRefusedWhenNotSubscribedOnThisLink`, `pendingEchoSurvivesReconnect`).
- **A deleted chat is inferred only from the list.** Subscribing to a deleted or unknown chat returns an empty `history`, not an error (`HB:1411-1420`, `HB:2229-2239`), contrary to the iOS comment at `AM:2949-2953`. The phone latches "deleted" only from an authoritative list (`AM:2877-2900`). A refused `deleteChat` comes back as an unsolicited `error` (no request ID, `HB:458-470`), the fast path to a refetch. Pinned in *Chat Repository* (`emptyHistoryIsNotDeletion`, `chatMissingFromListIsDeleted`) and *Chat Management* (`refusedDeleteRefetchesAtOnce`).

## Decided

The owner's answers to the draft's open questions and to the questions this revision raised, written into the tasks above:

1. **Watch every chat** for live states, plus the open conversation; no top-N set. Cost is designed down (bounded concurrent subscribes, never twice on a link, decode off the receive loop) and measured in the device check's *Reconnect cost*.
2. **Very large chats:** an 8 MiB chat history cap judged by length before parsing, "too large" above it; streaming decode is a later phase; memory tests assert peak allocation, never retained heap or time.
3. **Port `RemoteCommand.markdownDescription` now**, so the Waiting card shows the command; cards stay read-only.
4. **Switching tabs away from a live session closes its stream.**
5. **Full command argument** in a selectable monospace block under the Waiting card when `markdownDescription` cut it at 32 characters, an Android addition beyond iOS.
6. **A chat found too large is not resubscribed** for the rest of the process (cap confirmed at 8 MiB).
7. **"Go to session" checks existence now:** `fetchSessionScreenInfo` is ported so a raw-guid chat shows the button only once the Mac confirms the session, as iOS does (`AM:4256-4276`).
8. **Two concurrent subscribes** with the suspect retry for an over-cap history (revised: suspects go **first** and alone, right after the link comes up, one at a time, before any other chat), and **iOS's move from the Chats root to Sessions** when AI turns off.
9. Inferred Waiting with the request latch; Chats is the default tab when AI is available, decided once per process; 5 s workgroup polling, paused when backgrounded or disconnected; inline image budgets kept; seen marks persisted; the session view's chat button left out.
